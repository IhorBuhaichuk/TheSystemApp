# 01. Чи правильно підібрані технології

## Висновок простою мовою

**Так, поточний вибір правильний для Android-first.** На Kotlin/Compose можна зробити і швидкий журнал, і складний анімований HUD, і локальні рекомендації, і інтеграції з Android. Інша мова сама по собі не додасть ні плавності, ні кращих тренувальних рішень.

Потрібно розрізняти три речі:

- Мова: Kotlin, JavaScript/TypeScript, Dart, Swift.
- Платформа/UI: Android Compose, React Native, Flutter, SwiftUI.
- Якість реалізації: обсяг роботи під час відкриття екрана, запити до БД, обробка подій, рендеринг, життєвий цикл, тестування.

Погано організований запит до всієї історії залишиться проблемою і після переписування на TypeScript. Натомість точкове виправлення запиту може допомогти без зміни UI-платформи. Саме в цьому коді `DecideTodayWorkoutUseCase` ще читає `getAllLogs()`, хоча Statistics уже використовує обмежений період. Це кандидат на вимірювання, не доказ причини всіх затримок. [E03, E10](06-EVIDENCE.md).

## Що фактично використовується

Версії нижче прочитані з репозиторію 2026-10-08. Це інвентаризація, а не твердження «усе найновіше» і не сертифікат сумісності.

| Частина | Поточний стан | Моя оцінка |
| --- | --- | --- |
| Kotlin / Coroutines / Flow | Kotlin 2.1.0, Coroutines 1.9.0 | Залишити; добре відповідають станам і асинхронній роботі Android |
| Compose | BOM 2026.04.01, власні SystemTheme/SystemPanel/techSurface, Material3 | Залишити; власний стиль не потребує власного UI-двигуна |
| ViewModel + Hilt | Hilt 2.59.2 | Залишити; уже інтегровані залежності та тести |
| Room | Бібліотека 2.8.4, схема 53, 30 таблиць | Залишити; виправляти цілісність і backup-політику, не міняти БД |
| Модулі | `:app`, `:domain`, `:baselineprofile` | Достатня основа; не дробити на десятки модулів без вимірюваної потреби |
| Build | AGP 9.1.1, Gradle 9.3.1, JDK target/toolchain 17, KSP 2.1.0-1.0.29 | Потрібен керований супровід сумісного набору |
| Android | minSdk 26, compileSdk/targetSdk 36 | Реальні device/release-тести важливіші за сам номер SDK |
| Navigation | Navigation Compose 2.9.8 | Не міняти посеред стабілізації лише через появу новішого підходу |
| Фонові задачі | WorkManager 2.11.2 | Доречний для відкладеної роботи; не джерело гарантії точної опівночі |
| Health Connect | 1.1.0, тільки читання сну | Правильний вузький обсяг, інтеграція ще має незавершені частини |
| Зображення / JSON | Coil 2.7.0, kotlinx.serialization 1.8.1 | Доречні; оновлювати окремими перевірюваними змінами |
| Gemini | `com.google.ai.client.generativeai:0.9.0`, у release вимкнений | Найочевидніша залежність для майбутньої заміни перед public AI |
| Перевірки | JVM/Room guards, Compose instrumentation, CI, benchmark-модуль | Уже є основа; потрібне виконання важливих сценаріїв, не лише наявність файлів |

Докази: [E00, E01, E05, E09, E11](06-EVIDENCE.md). Загальний напрям узгоджується з [рекомендаціями Android](https://developer.android.com/topic/architecture/recommendations).

## А якщо використати мови з Full Stack курсу

Точний стек твого курсу невідомий. Якщо це HTML/CSS, JavaScript/TypeScript, React і Node.js, це корисні знання, але не автоматична причина змінювати Android-застосунок. Якщо курс був на Java, C# або Python, базовий висновок той самий: знайомство з мовою треба порівнювати з вартістю перенесення вже створених функцій.

| Варіант | Коли має сенс | Що це означає саме тут |
| --- | --- | --- |
| Kotlin + Android Compose | Android є основною платформою; потрібні інтеграції та контроль локального UI | Найменший ризик і найкраще використання наявної роботи |
| React Native + TypeScript | Одночасний Android/iOS, сильна TS-команда, готовність підтримувати native інтеграції | Можливий якісний продукт, але Room/Hilt/Compose UI не переносяться механічно. Це масштабне переписування |
| Flutter + Dart | Важлива спільна UI-кодова база для платформ, команда свідомо обирає Dart | Власна модель UI; усе одно потрібні інтеграції та перевірки Android. Немає доведеної переваги для нинішнього коду |
| Kotlin Multiplatform | Пізніше з'явиться підтверджена потреба в iOS і спільних бізнес-правилах | Найцікавіший шлях дослідження без відмови від Kotlin; не запускати міграцію зараз |
| Swift/SwiftUI | Окремий нативний iOS-клієнт | Доповнення, а не заміна Android-коду |
| Web/PWA/WebView-оболонка | Веб-сервіс, контент або простіші сценарії з іншими платформними вимогами | Не рекомендую для основного продукту; суперечить поточному Compose-only правилу репозиторію |
| C++/Rust/Python для клієнта | Спеціальна обчислювальна задача або окремий інструмент | Немає підтвердженої потреби; ускладнення не дає автоматичної вигоди |

Порівняння є моїм висновком для цього репозиторію, а не загальним рейтингом фреймворків. React Native не є «React-сайтом у телефоні» і не потрібно вважати його завідомо повільним. Flutter теж не гарантує швидкість незалежно від коду. Див. [React Native architecture](https://reactnative.dev/architecture/landing-page), [Flutter architecture](https://docs.flutter.dev/resources/architectural-overview), [Android: Kotlin Multiplatform](https://developer.android.com/kotlin/multiplatform).

Окремий `:domain` допоможе можливому KMP, але він сьогодні є Kotlin/JVM, а не готовим `commonMain`: є `java.time`, JVM-типи та injection-залежності. «Чистий від Android» не означає «автоматично кросплатформний».

### Де знадобляться Full Stack навички

Пізніше: окремий сайт продукту, privacy/support-сторінки, інструменти контенту, сервер для платного AI чи синхронізації. Сервер може бути на TypeScript або Kotlin і не вимагає переписування мобільного клієнта. Це майбутні окремі задачі, не дозвіл генерувати web UI в цьому Android-репозиторії.

Для самостійного контролю Android-роботи найвигідніше вивчити: nullable Kotlin, `data class`/`sealed interface`, Flow і coroutine cancellation, Compose state, навігацію, SQL-транзакції та читання тестів. Це дасть більше незалежності від AI, ніж зміна всього стеку на знайомий синтаксис.

## Що справді переглянути

### 1. Підтримуваний AI SDK, але лише коли вмикатимемо public AI

Наявний Google AI Android SDK офіційно deprecated і його репозиторій архівований. Це конкретна проблема супроводу, а не ознака неправильності Kotlin. [Офіційний репозиторій SDK](https://github.com/google-gemini/deprecated-generative-ai-android).

Перед public AI обрати підтримуваний шлях: Firebase AI Logic із захистом клієнтських викликів або власний серверний API з авторизацією, лімітами й бюджетом. Обидва варіанти потребують обліку того, які тренувальні дані залишають пристрій. Не вшивати Gemini-секрет у release APK; не прирівнювати клієнтську Firebase-конфігурацію до серверного секрету. [Firebase production checklist](https://firebase.google.com/docs/ai-logic/production-checklist).

Firebase AI Logic не означає обов'язкове підключення Firebase Analytics. До доведеної потреби можна залишити локальний режим. Зберегти `ValidateDirectivesUseCase` між зовнішньою порадою й зміною тренувальних цілей.

### 2. Узгоджений build-toolchain

У `gradle.properties` є `android.builtInKotlin=false` і `android.newDsl=false`. AGP 9 підтримує built-in Kotlin за замовчуванням; чинний opt-out потребує свідомого супроводу. Не видаляти прапори наосліп: перевіряти AGP/Kotlin/KSP/Compose compiler/Hilt/Room як сумісний набір. [Android migration guide](https://developer.android.com/build/migrate-to-built-in-kotlin).

Результат має бути не «оновили все», а відтворювані compile, unit tests, Room migration, lint і release bundle. Поточний аналіз не запускав їх заново й не стверджує, що цей набір сьогодні проходить усі gates.

### 3. Узгоджений стан onboarding і backup

Для невеликих налаштувань можна розглянути DataStore. Але заміна SharedPreferences сама не зробить запис у Room і прапор onboarding однією транзакцією. Спочатку визначити, що означає завершене налаштування і як воно відновлюється. Це проблема контракту стану, не просто вибору бібліотеки. [DataStore](https://developer.android.com/topic/libraries/architecture/datastore), [E02, E06](06-EVIDENCE.md).

### 4. Performance-інструменти використовувати, а не додавати повторно

`baselineprofile` і startup journeys уже існують. Потрібні повторювані вимірювання release-like збірки на тому самому пристрої: перший запуск окремо від cold/warm, час до інтерактивного Today Order окремо від першого кадру. Старе спостереження про 5.3 с не є актуальним benchmark цієї сесії.

Спочатку trace -> причина -> одна зміна -> повторний вимір. Кандидати: обсяг історії в decision, повторні flows, важкі HUD draw/layout, зображення. Версіонування seed уже є; не описувати його як відсутнє. Baseline Profiles можуть допомогти hot paths, але не виправляють некоректну логіку та не гарантують певний відсоток прискорення. [Baseline Profiles](https://developer.android.com/topic/performance/baselineprofiles/overview).

## Що не додавати зараз

- Новий DI-фреймворк, MVI-бібліотеку або десятки модулів тільки для «сучасності».
- Другу БД, backend, облікові записи й синхронізацію без доведеного користувацького запиту.
- AGSL/Lottie/3D та постійні blur-ефекти як ліки від недостатньо цікавого UX. Спочатку використати існуючі Compose animation APIs і motion-токени.
- ML-модель для readiness лише заради AI-лейбла: спочатку потрібні якісні дані, прозорі правила й перевірка тренувального змісту.
- Навігаційну міграцію одночасно з виправленнями logging/restore. Нові API варто оцінювати окремо, а не масово впроваджувати.

**Умова для перегляду стеку:** якщо одночасний iOS-запуск стане обов'язковим бізнес-рішенням, проведемо короткий технічний spike одного реального сценарію й порівняємо вартість. До цього Kotlin/Compose не є обмеженням потенціалу.
